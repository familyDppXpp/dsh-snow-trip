# 雪季出行首页实施规格

## 1. 问题与目标

当前应用从“已录套餐”或上次会话进入，左上角“雪季出行”没有返回首页的行为。用户需要一个统一首页，通过两种可切换的视图了解套餐与方案在时间、地点上的分布。

本规格基于本次已确认的访谈与当前工作区代码。只生成本地文档，不修改产品代码，不发布外部 issue。`ready-for-agent` 为本地标记，不表示地图服务已配置或功能已经验收。工作区已有未提交的套餐、方案筛选等改动，实施必须保留并在其基础上集成。

## 2. 已确认的产品决策

| 项目 | 决策 |
| --- | --- |
| 首页入口 | 打开应用默认进入首页；点击“雪季出行”返回首页；保留套餐、方案和会话入口 |
| 展示方式 | 月历与地图是两种切换视图，不做月历与地图的双向联动 |
| 视图偏好 | 首次默认月历，之后记住上次选择 |
| 月历内容 | 同时展示套餐可用日期与方案行程日期，两类内容分开 |
| 日期格 | 显示套餐数量、方案数量；点击后在下方展开明细 |
| 套餐日期口径 | 当晚允许入住即计入，不要求从该日开始能完整用完套餐；明细解释连住和补款限制，不代表实时有房 |
| 地图范围 | 默认全部已录套餐和已存方案，可按月份筛选 |
| 地图粒度 | 具体酒店与雪场，使用不同图标；两者都展示，套餐、方案按各自 ID 去重 |
| 定位方式 | 按名称与地区自动查找；有歧义时交由用户选择；无法定位的条目单独列出 |

后文未在访谈中单独讨论的日期边界、首次月份、接口、缓存等属于本规格的实施默认值，不冒充用户逐项确认的决定。

## 3. 用户故事

1. 作为用户，我希望打开应用就进入首页，以便概览已有套餐与出行方案。
2. 作为用户，我希望从任何页面点击“雪季出行”返回首页，以便随时重新浏览。
3. 作为用户，我希望在月历和地图之间切换并记住选择，以便按习惯查看同一批资料。
4. 作为用户，我希望切换年月并返回本月，以便查看不同时间的出行机会。
5. 作为用户，我希望每天分别显示套餐与方案数量，以便区分可选资源和已保存的安排。
6. 作为用户，我希望点击日期后查看明细和限制，以便判断当天是否适合出行。
7. 作为用户，我希望日期规则不全的套餐标为待确认，以免把未知误认为可用。
8. 作为用户，我希望看到跨月行程且不会重复计数，以便正确理解行程分布。
9. 作为用户，我希望地图分别标出酒店和雪场，以便了解住宿与滑雪的位置关系。
10. 作为用户，我希望点击地点查看关联套餐、方案，以便进一步查看详情。
11. 作为用户，我希望地图可以筛选月份并恢复全部，以便按时间缩小地点范围。
12. 作为用户，我希望同一记录关联多个地点时总数仍然准确，以免误判拥有的套餐或方案数量。
13. 作为用户，我希望系统自动定位明确的地点，以便减少重复录入。
14. 作为用户，我希望查看同名候选的名称和地址后选择正确地点，以免地图标错位置。
15. 作为用户，我希望无法定位的记录仍可阅读并重新查询，以免记录从首页消失。
16. 作为用户，我希望确认过的位置重新打开后仍然保留，并能纠正错误选择，以便保持位置准确。
17. 作为用户，我希望保存或修改资料后首页及时更新，以便查看当前记录，同时保留已存方案的历史信息。
18. 作为用户，我希望地图服务不可用或资料读取失败时看到明确状态和重试入口，以便继续使用可用部分。
19. 作为用户，我希望没有记录时能直接开始录入，以便建立自己的出行资料。
20. 作为用户，我希望在手机和键盘操作下也能完成浏览、切换和查看明细，以便不依赖鼠标或大屏幕。
21. 作为用户，我希望从首页打开详情或会话后保留未发送草稿，以便继续原来的工作。

## 5. 首页交互与状态

- 新增 `home` 页面状态，面包屑为“我的雪季 / 首页”。品牌使用有可访问名称的按钮，支持键盘；移动端标题提供相同行为，点击后关闭侧栏。
- 每次重新打开工作台默认进入首页，包括已有上次会话的情况；仅保留会话引用与草稿，不自动跳到会话。显式打开会话、套餐引用等用户动作仍正常导航。
- 首页上方提供“月历 / 地图”切换。只持久化视图偏好，可使用命名空间化 localStorage；存储失败退回当前内存，不能阻断首页。定位信息不得放入该偏好存储。
- 月历首次显示用户本地时间的当月，周一开头；提供前月、后月、年月选择与“本月”。不固定为 26/27 雪季。初次不选日期，下方提示选择日期；切月清除日选择。
- 当前打开期间保留两种视图各自的月份/选择；重新打开后地图恢复“全部月份”，月历恢复当月，只恢复视图种类。
- 日期明细先显示方案，再显示套餐，分区标题明确；点击条目复用现有详情/会话路径，返回首页保留本次浏览状态。
- 地图月份与月历月份互相独立。筛选后选中地点已无记录时清除选择。首次自动适配全部已定位点，月份筛选后重新适配；普通重绘不重置用户缩放。
- 桌面日期明细位于日历下方；移动端保持同一顺序。地图需有可键盘访问的地点列表，提供与点位等价的明细操作。地图加载不抢走焦点。

## 6. 时间与计数规则

### 6.1 套餐

日期按 `YYYY-MM-DD` 的日历日处理；当前日取浏览器本地日期，区间加减复用已有日期辅助，避免 UTC 转换使显示偏移。

“可用套餐 N”准确含义为“日期规则允许当晚入住”，不是可预订库存或完整行程可用性。日历附近常驻此说明；购买状态不影响日期分布，但明细保留购买标签。

| 条件 | 日历行为 |
| --- | --- |
| `voided === true` 或已知剩余间夜为 0 | 不计入可用数；仍可在全部地图中查看，保留状态标签 |
| 当日明确早于 validFrom、晚于 validTo，或在已知 unavailableDates 中 | 不计入；有效期首尾日都包含 |
| 有效期两端已知、当日落在区间内、unavailableDates 是数组且不含当日 | 计入单晚日期可用数；空数组表示已知无禁用日期 |
| 日期依据不足，如有效期缺端或 unavailableDates 为 null | 不计入确定可用数；已知日期边界内列为“待确认”，不把 null 当空数组 |
| 剩余量、作废状态或拆分规则未知 | 不推断为已耗尽/已作废；明细标出未知，不宣称已满足完整使用条件 |

每格至少显示两类确定数量；存在日期待确认条目时附带“待确认 N”。完全缺乏日期的套餐集中在“日期待确认”列表，不铺满所有日期格。有部分日期边界时仅在不被已知条件排除的日期中提示待确认。套餐 ID 是计数单位，多酒店与多份方案引用不增加数量。

连住、拆分、补款规则原文在明细展示，本次不新建自然语言规则解析器，也不计算补款。已有明确日期字段与待澄清问题冲突时提示核对，不自行覆盖记录。

### 6.2 方案

- 优先按 `start` 至 `plusDays(start, nights)` 展示，包含离店日；这表示行程天数，区别于套餐的入住夜。
- 同一日一份方案最多计数一次；备选方案仍是独立方案，已保存不等于已预约，展示原 tracking 标签。
- 总起始日或晚数缺失时，以合法 `items` 的分段起止日并集展示，并标注“按分段日期展示”；不把分段间空档补成行程。
- 总日期与分段日期都无法确定的记录进入“日期待确认”列表，不编造行程日期。
- 跨月、跨年按区间相交显示，月底不截断真实行程；月份计数按方案 ID 去重，不能把每天数量相加当作方案总量。

### 6.3 地图月份筛选

- “全部月份”包含全部当前套餐与全部已存方案，包含历史、已耗尽、作废记录，但保留状态。
- 指定月份：套餐至少一天确定可用则计入月份确定结果；存在可能落入月份但日期不足的条目放入日期待确认分组，不混入确定计数。明确不可用的套餐不进入该月份结果。
- 方案按实际行程日期与月份相交判断。多段方案仅将该月相交分段关联的地点标为当月地点，避免把其他月份的酒店带入；快照关联不全时标注待确认。
- 已知坐标但日期待确认的结果可单独展开，不默认混入当月确定点位；所有待确认列表都保留详情入口。

## 7. 地图与定位

### 7.1 接入选择与外部条件

本规格的技术选择为高德地图 JS API 2.0 展示底图，宿主通过高德 POI 2.0 关键字搜索查找地点，不增加地图 React 包或通用多供应商框架。该选择属于实施决定，不是访谈中用户指定的供应商。

官方资料： [JS API 加载](https://developer.amap.com/api/javascript-api-v2/guide/abc/load)、[JS API 安全配置](https://developer.amap.com/api/javascript-api-v2/guide/abc/jscode)、[POI 2.0 搜索](https://developer.amap.com/api/webservice/guide/api-advanced/newpoisearch)。POI 查询需要 Web 服务 Key；JS API 需要对应的浏览器配置。实际额度、授权和部署域名限制以配置账户为准，本规格不承诺免费或无限调用。

接入条件是有效的 JS API Key、安全配置与 Web 服务 Key。目前只确认仓库没有地图接入，未读取个人凭据，也未验证可用额度。实施时通过插件宿主配置传入，不写入仓库或日志。Web 服务 Key 只在宿主使用；浏览器只拿公开地图初始化配置。JS 安全密钥采用官方安全代理配置，代理必须限定地图所需上游，不提供任意 URL 转发。该代理与宿主的可用接入方式应在地图集成开始时验证，不默认为宿主已提供。

缺少配置时显示“地图服务未配置”，保留地点列表及月历。此状态是降级处理，不能作为自动定位与真实地图完成验收的替代。地图供应商未覆盖的地点进入待定位，不伪造为国内同名地点；本轮不新增第二套海外地图服务。

### 7.2 地点提取与去重

- 当前套餐从 `hotels[]` 提取酒店，从 `resort` 提取雪场，地区来自 `region`；已存方案从所关联的 `packages[].snapshot` 提取。方案快照中的多个适用酒店标注“套餐适用酒店”，不暗示已选定入住酒店。
- 一个名称字段先作为一个待查询地点；不擅自按斜杠等字符拆出多个实体。模糊集合名称留待用户选择或通过原有流程补充资料。
- 查询身份为供应商、类型、规范化名称、地区；只做去首尾空白和连续空白合并，不删除可能区分门店的文字。
- 地图点位按供应商 POI ID 去重；同一 POI 同时承担酒店和雪场角色时显示两个角色标识。地址相同或坐标接近不意味着同一 POI。
- 点位的套餐数只统计当前套餐 ID；方案数只统计方案 ID。历史快照用于关联方案，不作为新套餐计入。页面总数为各 ID 集合大小，不能相加点位数量。
- 点击点位展开完整名称、类型、地址与两个记录列表。附近点重叠时可通过等价地点列表逐个选择，不引入额外聚类框架。

### 7.3 自动查找与用户确认

首次进入地图时提取去重后的地点，优先读宿主缓存，仅查询缺失项；切换月份不重复查询已解析地点。使用固定并发上限 2、单请求超时 10 秒；失败由用户重试，不后台无限重试。

查询使用名称、地区和地点类型。地区是自然语言时用作检索上下文，不把“长白山”等目的地强行当成合法行政区代码。返回坐标必须是有效有限数值，经纬度范围合法，并标记供应商坐标系。

自动接受条件：候选中仅有一个名称规范化后完全匹配、类型相符且地区可验证相符的 POI。只有一个模糊候选也不自动接受；缺地区且不能证明唯一时仍待确认。不得以搜索排名第一作为自动确定依据。

多个候选在“待定位”中显示名称、地址、类型，让用户选择；没有结果时允许改检索词/地区后重试，检索词修正不改写原套餐名称。已定位地点提供“更正位置”，重新选择后更新共享地点解析结果。用户手选不被后续自动查询覆盖。

仅将地点名称、地区与类型发送给地图服务，不发送价格、方案全文、会话或用户身份。外部响应作为数据处理，不能作为指令；显示用文本渲染，避免拼入未转义 HTML。

## 8. 数据结构与接口契约

以下为本插件拟新增契约，不是当前已存在的 DSH API。沿用 `TypertRemoteService`、宿主认证与构建生成的 Remote 类型。

### 8.1 持久化

在 `snow_trip` 域追加一张 `places` 表，不修改 packageRecord / planRecord，不重写历史快照。确认存储库的追加表兼容方式后按其机制升级域版本，必须验证旧数据仍可读，不能通过清空库升级。

每条地点解析记录包括：查询身份键、原始名称、地区、类型、provider、解析状态、更新时间，以及已解析的 POI ID、展示名称、地址、经纬度、坐标系和来源（自动/用户确认）。已确认记录保存当前版本号，用于并发更正校验。未解析状态区分“候选待确认”“无结果”；临时网络错误单独返回，不覆盖成功记录。

候选结果保存在宿主短期内存中并返回不透明查询 ID；用户确认只提交查询 ID 与候选 ID，服务端从实际查询结果中读取位置，不信任客户端任意坐标。候选失效时明确提示重新查询。记录名称或地区变化后生成新查询身份，不沿用旧身份坐标；历史快照仍能复用旧身份记录。

### 8.2 最小 Remote 表面

| 操作 | 输入 | 输出及约束 |
| --- | --- | --- |
| `getMapConfig` | 无 | 可用状态、公开 JS Key、安全代理地址；不得返回 Web 服务 Key 或安全密钥 |
| `resolvePlaces` | 最多 50 个套餐/方案地点引用 | 引用指向 record ID、快照套餐 ID（方案时）、类型及酒店下标；宿主从已存记录取文本，返回已解析项、候选或逐项错误；只查询未缓存项 |
| `searchPlace` | 一个合法引用、用户修正的检索词与地区 | 有限候选、查询 ID、解析状态；校验长度，满足上游关键词限制，不允许用户指定上游 URL |
| `confirmPlace` | 查询 ID、候选 ID、期望版本 | 写入用户确认的位置并返回最终记录；版本冲突、候选过期或保存失败时不显示成功 |

批量返回保留每个引用的对应关系与独立错误。已有缓存的读取不依赖供应商在线；多批加载逐步显示。宿主按查询身份合并正在进行的重复请求，用户确认与自动结果写入需序列化校验，避免迟到响应覆盖人工选择。

无需新增模型工具或更改录入技能：本轮地点查询是首页显式地图功能。地图脚本按需加载一次，离开视图销毁地图实例与事件；保留解析数据，取消过期界面更新。

## 9. 失败、空态与一致性

- 套餐、方案分别显示加载/读取失败和重试入口，不能把尚未加载或失败显示为 0；一类失败不阻止另一类展示，汇总标明部分数据。
- 没有任何记录时提供“开始录入”；某月/某日无匹配与全库为空区别处理。
- 地图脚本、网络、授权或配额失败：保留已加载记录和地点列表，显示对应错误与重试；不把网络失败缓存为“找不到地点”。
- 缺少酒店和雪场名称、查无结果、有歧义分别给出原因；未知地区不等于未知名称，仍可查询但不得草率自动确认。
- 保存地点失败保留候选与选择；再次提交成功前不声称已保存。已定位项更正失败时保留上次成功位置。
- 复用当前会话更新触发的数据刷新；记录修改、删除后重建日期与地点关联，清理失效的界面选择。旧请求晚到不能恢复已删除条目。
- 返回首页、切换视图不能停止宿主正在执行的会话或清空草稿；不自动发送消息、不重新核算方案。

## 10. 验收与测试策略

优先通过已有公开操作与真实 App 验证。只对外部地图查询设置确定性响应替身，不对每个内部函数建立 mock。自动测试不依赖个人真实数据、模型费用或实时供应商结果。

| 层次 | 最小覆盖 |
| --- | --- |
| 日期/聚合行为测试 | 有效期首尾、禁用日、null 与空数组、未知使用量、已耗尽/作废、跨月跨年和闰日、包含方案离店日、分段并集及去重 |
| 宿主接口集成 | 从真实记录提取引用；唯一匹配自动接受；歧义不猜；手选保存与重启后读取；并发不覆盖手选；过期候选/非法引用拒绝；上游失败不破坏已保存位置 |
| 真实 App 浏览器 | 默认首页、品牌返回、切换记忆、日期展开、独立地图月份、双角色点位与去重、未知分组、重试、手机宽度和键盘操作、草稿保持 |
| 实际宿主冒烟 | 用已配置的地图服务验证脚本加载、一个酒店与一个雪场的真实点位、人工选择歧义候选及刷新后保留；不使用生产记录做破坏性测试 |

具体断言示例：套餐 A 有效期 12 月 30 日至次年 1 月 2 日，1 月 1 日禁用，剩余间夜大于 0。它在 12 月 30、31 日及 1 月 2 日各计 1，在 1 月 1 日计 0，不因不能从 1 月 2 日住满套餐晚数而排除。方案 B 从 12 月 31 日住 2 晚，则 12 月 31 日、1 月 1 日、1 月 2 日各计 1。A 同时关联酒店和雪场时各点可关联 A，但全图套餐总数仍为 1。

再加入套餐 C：有效期相同但 unavailableDates 为 null，应在日期待确认中显示，不能使确定可用数加 1。方案 B 引用多个同地套餐也只能在该地点计 1 份方案。套餐名称/地点更新后，B 仍展示原快照地点。

实施后执行 `pnpm typecheck`、`pnpm test`、`pnpm build`，并沿用 `SNOW_PLAYWRIGHT`、`SNOW_REACT_DOM`、`SNOW_CHROME` 环境运行新增首页浏览器检查。现有默认进入已录套餐的测试需先显式导航到已录套餐，其原有业务断言保留；会话恢复测试相应调整为“先首页，再主动打开原会话”。不得只改测试断言绕过导航回归。

实施完成条件：上述可重复测试通过，并记录真实地图冒烟结果。无凭据时可以完成本地逻辑和降级验证，但真实地图/自动查找验收必须明确标为未完成。本文是规格交付，不声称已运行实现测试。
