源码课程 01 · 雪季工作台 · 当前本地 DSH

DSH 消息界面：结构与定制边界

目标：面对新的界面需求，判断该扩展哪一层、能复用什么，以及什么时候需要宿主配合。问答卡片故障只作为贯穿示例。先区分四样东西：发生了什么的事件、工具返回的内容、准备展示的节点、最终画出来的组件。这次故障卡在“内容 → 节点”，问答组件本身还在。

全景 · 数据链与界面树是两张图

数据怎么到界面：

模型 / 工具 / 人类交互→ 会话事件与状态→ SessionBinding 的事件源→ Conversation 装配→ 各 target 的快照→ React 订阅与渲染

这里把模型、工具到事件源之间的服务传输概括为一层；本课重点是消息界面架构，不展开网络协议。持久化内容与运行时待交互状态不能混为一谈。

界面怎么嵌套：

主应用 / 自定义工作台
└─ 会话外壳（ui-conversation）
   ├─ header：标题、操作、视图导航
   └─ 会话内容（conversation.content 工厂）
      ├─ 当前视图（conversation.view）
      │  ├─ chat：聊天时间线（ui-chat）
      │  │  ├─ 用户 / 助手 / 执行过程 / 自定义节点
      │  │  └─ 工具树 → 工具专用视图（ui-tool）
      │  └─ 插件注册的其他视图
      └─ composer：常驻输入位置
         ├─ 普通输入框、附件、模型选择等
         └─ 待交互时的问题卡 / 确认卡

输入区不属于某条助手消息；工具专用视图不等于独立聊天节点；自定义工作台也不必自己重新实现整套聊天。这三个边界决定你把 UI 放在哪里。

定制地图 · 从最小局部到整套工作台

你想做的 UI扩展位置能做到与需要承担的事
把某个工具结果显示成表格、图表、订单卡tool.call.toolview，按工具名 keyed复用工具生命周期和工具树。它仍受所在工具/执行过程布局影响，不保证永远独立展开。
把结果作为独立卡片留在消息流uiConversation.events + conversation.chat.node定义事件到节点的转换，再注册 React 组件；负责配对、解析、错误和历史回放。问答记录就是例子。
在用户回答前显示专用表单conversation.composer 的 chain按 pendingInteraction 选择表单。表单提交必须接到真实交互协议，单画按钮不会让工具继续执行。
加输入框按钮、附件区、悬浮菜单conversation.input.left / right / overlay / attachments 等可定制局部 UI；通过 inputActions 等输入接口操作草稿与发送，不只改 DOM。
改标题、加详情开关、轮次末尾内容header.actions / utilities；conversation.chat.turnTail保留宿主会话结构，在明确的位置加入口。雪季右侧关联资料开关就是这种做法。
改默认消息、运行过程的外观conversation.chat.node 对应 kind可在合适作用域贡献替代呈现；仍要遵守槽位选择规则。雪季工作台替换了 turn-process 的显示。
同一会话提供时间线、看板等另一种视图conversation.view + uiConversation.views；必要时新增事件定义不是只换一个组件：需要自己的 target 快照构建、节点组织和视图组件；原始会话可复用。
做完整业务工作台自定义布局 + 会话内容工厂 + 局部插件作用域侧栏、业务页、详情面板可自己组织，嵌入宿主会话能力。雪季现有实现已做到这一层。

这些是当前源码存在的扩展点，不代表任意槽位都可无条件覆盖：要匹配作用域、父槽位声明、注入依赖和注册规则。缺少真实数据或服务能力时，前端扩展点并不能替你提供它。

槽位 · 宿主如何把控制权交给插件

Slot 是一个有契约的界面位置。宿主在这个位置调用 renderSlot，插件提供组件。组件拿到的是该槽位声明的数据、回调和订阅入口，而不是随意访问整个宿主。

类型理解方式本地例子
single一个位置选出一个呈现conversation.input.model
list按规则组织多个贡献项conversation.session.header.utilities
keyed按指定键找呈现chat.node 按 kind；toolview 按工具名
chain按选择条件处理当前状态composer 在待回答时采用问题组件

root、session、session-maybe 是不同上下文：例如模型选择需要当前会话，空白欢迎页可能还没有会话。把组件装错上下文，可能出现“代码存在但不显示”或缺少服务。

雪季插件还 isolate 了 slots、uiConversation 等服务，重新装配局部 UI。局部替换不会自动等于全局 DSH 的替换；代价是要维护所复用插件的契约与生命周期。

边界 · 纯界面变化与业务能力变化

纯客户端通常足够：改卡片布局、添加图表、改变节点展示、添加输入控件、用已有事件做另一种视图。这些变化仍需校验当前槽位契约。

客户端与宿主插件需要协作：新表单需要暂停任务等待确认、新按钮要保存套餐、新卡片要展示之前从未提供的数据。宿主工具或服务负责执行与存储，前端负责交互与显示。可用工具结果或展示 metadata 提供历史卡所需快照；不能只放 React state 就期待刷新恢复。

可能需要改宿主核心：需要的底层生命周期、事件、输入行为或布局控制没有公开扩展点，又不能通过自定义视图或插件服务实现时。不能因为默认聊天长得不合适就直接判断必须改核心；先看能否换 view 或外壳。

两个不可省略的边界：渲染节点不等于模型上下文消息，显示一张卡不会自动给模型增加信息；界面隐藏权限按钮不等于权限约束，保存、校验和执行权限仍由相应服务负责。

需求选择练习：希望展示一张“报价对比图”，刷新后仍在，点击“采用”还要写入业务数据。至少应分别决定显示位置、历史数据来源、点击执行协议这三件事。

01 · 先看断在哪里

旧解析器期望的结构与当前结果如下。这是省略其他字段的结构示意，不是完整事件协议。

// 旧解析器期待
message.content = [{
  type: 'tool-result',
  content: [{ type: 'text', text: '{"answers":[...]}' }]
}]

// 当前 ask_user_question 结果
{
  type: 'tool/result', surfaceOp: 'append', seq: 12,
  data: { message: {
    source: { callId: 'q1' },
    content: [{ type: 'text', text: '{"answers":[...]}' }]
    // 错误时检查这里的 isError
  }}
}

tool/result 命名一次会话事件；text 命名消息里的内容块。问答工具将结构化答案序列化为 JSON 文本，所以需要 JSON.parse。不能据此推断所有工具结果都只有文字。

旧代码找不到 type='tool-result'，提前返回旧状态；状态没有 answers → buildViewNode 返回 null → 渲染槽位根本收不到这张卡。不是 CSS 隐藏，也不是卡片代码被删。

依据：资料 1、9、11；旧结构来自本插件修复前的解析逻辑，不代表所有旧宿主事件。

02 · 新宿主的消息渲染主干

会话事件源→ 装配器→ 节点定义与状态→ 视图快照→ 槽位组件
层做什么本例
事件源提供已加载历史与后续事件窗口tool/call、tool/result
装配器 / 定义匹配事件，按定义与标识维护状态同一个 callId 的问题与答案配对
视图节点声明目标、位置、类型、数据和可见性kind='snow-question-answer'，target='chat'
聊天快照与布局组织顺序、分组和可观察的视图数据记录卡在答案事件处产生锚点
React 槽位按 node.kind 找注册的组件QuestionAnswerCard 接收 node.data

一个事件不一定对应一个气泡：多个流式事件可以更新一个助手节点；一对问题与结果事件可以合成一张记录卡。节点也不是 HTML，而是描述“该显示什么”的对象。

依据：资料 2–7、9–10。

03 · 沿问答卡走一遍

  1. tool/call：match 检查工具名 ask_user_question，用 callId 作为 id；start 从 arguments 解析 questions。
  2. 等待人类回答：宿主问答服务显示可交互问题，工具执行等待答案。此时记录定义没有 answers，不输出记录节点。
  3. tool/result：match 读取 message.source.callId，找到同一状态；update 检查 message.isError，从 message.content 的 text 块解析 answers。
  4. buildViewNode：有 answers 后生成节点。anchorSeq 使用结果事件 seq；location={kind:'session'} 表示这张插件卡声明的会话级位置，不表示所有消息都是会话级。
  5. 渲染注册：conversation.chat.node 以 snow-question-answer 为键找到 QuestionAnswerCard。组件按问题 id 配对答案，呈现选择、补充或跳过。
view.uiConversation.events.register(questionAnswerDefinition);
view.slots.inject('conversation.chat.node', () =>
  view.slots.register(
    {name:'conversation.chat.node', key:'snow-question-answer'},
    ({node}) => <QuestionAnswerCard data={node.data}/>
  )
);

这两次注册缺一不可：第一处负责把事件变成节点，第二处负责把节点画成卡片。宿主找不到对应渲染器时有 JSON 回退显示；但节点为 null 时不会进入这个回退。

05 · 普通文字、工具和历史回放

普通助手文字：assistantDefinition 以 turn:step 配对 step/start、assistant/live-chunk 和 assistant/message。text-delta、reasoning-delta 等更新中间状态；最终消息用于收定内容。流式可见更新采用 animation-frame 发布节奏，最终消息立即发布。因此“逐字增加”与最终消息走同一条状态装配链，而不是每个字创建一个新气泡。

普通工具：内置工具节点也直接读取 message.content 和 message.isError。它自己的 UI 数据仍可能出现 kind='tool-result'；这是界面的块类型，不能拿它当原始消息的嵌套协议。

历史回放：会话绑定订阅事件窗口。追加事件逐条 append，向前加载历史走 prepend，窗口替换或版本不连续会 replaceWindow。相同定义用于重新装配已加载的事件，因此旧的“原始问答事件仍在、仅解析有误”的记录有机会在修复后重新显示；缺失事件不能凭空恢复。

视图选择：装配接口支持多个 target，chat 是其中一个；本课聚焦当前聊天界面，不把这一界面当成所有宿主视图。

依据：资料 2–7。

06 · 两种问题卡，职责不同

待回答问题卡已回答记录卡
宿主 ui-user-questions 注册到 conversation.composer；跟随 pending interaction。雪季插件注册到 conversation.chat.node；从调用与结果事件合成。
收集用户答案，解除工具等待。展示已发生的回答，不重新提交或修改答案。

所以你可以正常答题、模型也收到答案，但历史卡仍不显示。这次修复的是右侧这条路径。

07 · 自查：先写判断，再展开

先做需求选层：① 工具折叠行里显示报价图；② 独立留在消息流的报价卡；③ 确认前暂停执行的报价表单。各落在哪个扩展点？再思考：工具结果已有 answers，但节点为空，与节点已有却显示 JSON，有什么不同？

展开核对

① tool.call.toolview；② 事件定义 + conversation.chat.node；③ conversation.composer + 宿主待交互能力。只改显示时无需凭空新增业务事件；需要保存与恢复时必须有相应数据来源。

A：检查 update 是否得到新 state，content 路径、isError、JSON 与 answers 类型，以及 callId 是否配对；只看到原始 answers 还不够。B：检查 conversation.chat.node 的 entryKey 与 node.kind 是否一致，渲染器是否在当前作用域注册。

下一步讨论：若只有 tool/result 没加载到 tool/call，本插件为什么可能无法生成完整问答记录？提示：查看 start 保存了什么，update 对缺失 state 做了什么。
