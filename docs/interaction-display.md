# 消息流与工具展示规则

原则：需要用户操作的内容以卡片承接；后台执行留在宿主普通工具记录中。

| 内容 | 等待用户时 | 用户操作后 |
| --- | --- | --- |
| 必要信息澄清 | 宿主提问卡 | 宿主保留问题与回答 |
| 套餐新增、修改 | 套餐确认卡 | 立即保留保存快照；继续调整、补充保留未保存状态和原文 |
| 出行条件、费用 | 可编辑确认卡 | 确认后只读条件快照；补充或取消保留原条件并明确尚未确认 |
| 推荐结果、讨论、回顾、状态入口 | 对应方案卡 | 保留查看的方案和用户动作、补充原文；保存逐项反馈成功或失败 |
| 查询、草稿编辑、方案核算、进度查询 | 普通工具记录 | 不额外插入大卡片；错误详情仍交给模型并留在工具记录 |

交互反馈使用独立消息节点，以该工具调用的 callId 为身份，固定在结果事件的位置；不是轮次结束时汇总的过程卡片。刷新从持久化 metadata 回放，不重新读取现价替换快照。

只有 prepared 表示出行条件已确认。补充、取消不得标成已确认，不得自动保存。模型收到补充原文后应继续处理；没有补充的取消才等待用户输入。

套餐确认前的技术校验错误只在工具记录展示。保存工具报错不能生成成功卡片；批量保存的部分失败必须逐项反馈。停止保留未保存状态。历史记录缺少补充原文或卡片快照时，不得编造补齐。

方案核算、进度查询不得注册业务卡片 toolview，也不得进入消息尾部卡片投影。交互后的反馈由专用消息节点渲染，避免在工具记录和消息末尾重复显示。
